ShopWarda · Architecture Blueprint 01

A modular commerce platform—clean enough for one developer, strong enough to grow

The recommended design keeps the storefront, admin, backend-for-frontend, and MongoDB domain layer in one Next.js codebase. Boundaries are enforced by modules, not extra servers.

Recommended

A · Next.js modular monolith

App Router + Server Components + Server Actions/Route Handlers + Mongoose.

  • One deployment and one type system
  • No internal HTTP calls from server pages
  • Modules can be extracted later

B · Split Next.js + Express

Classic MERN with a separate REST API and two deployable applications.

  • Useful when mobile/external clients are imminent
  • More auth, CORS, API versioning, and operations
  • Premature for one storefront

C · Microservices

Separate catalog, order, inventory, and analytics services with events.

  • Independent scaling
  • Distributed transactions and observability burden
  • Wrong size for ShopWarda v1

5. Non-negotiable architecture rules

These rules keep the codebase fast, secure, and understandable.

Guardrails
Anonymous cart authorityOpaque HttpOnly cookie + Mongo TTL. Optimistic UI mirrors the server; BroadcastChannel syncs tabs.
Money correctnessAll EGP values stored as integer piasters. Never use floating-point totals.
Admin securityproxy.ts performs only an optimistic redirect. Every page, action, and handler re-checks the admin session.
Private payment proofInstaPay screenshots use private assets and signed read URLs. They are visible on the order, not a separate approval gate.
Cache by domainCatalog/categories use cache tags. Cart, checkout, orders, sessions, and stock are never shared-cache data.
Thin routesPages and handlers validate, authorize, then call services. Business rules never live in React components.
Stock safetyConditional decrement inside a MongoDB transaction prevents selling unavailable variants.
Replaceable providersStorage and analytics sit behind interfaces: Cloudinary now; GA4 now; Meta Pixel later.
Shadcn disciplinePrimitives live only in components/ui. Store and admin compose them into domain-specific components.
